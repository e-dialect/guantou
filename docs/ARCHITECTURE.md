# 方言罐头架构说明

## 核心模型

`Can` 是一段具体录音，保存音频 URL、录制者、方言点、产地、状态、来源说明、审核可见性。它是系统的数据原子，可以先于稳定写法和释义存在。

`Nameplate` 是贴在罐头上的铭牌，表示“我认为这段录音应该这样写、这样解释、属于这个风味”。铭牌是连接罐头、风味和包装的主张实体，同一个罐头可以有多张铭牌，`weight` 和 `is_primary` 决定默认展示。系统保留低权重铭牌作为异议和考据记录，不用覆盖式写入抹掉少数观点。

`Flavor` 是语义核心，表示一个义项或概念，例如“行走”“祖母称谓”。风味的粒度以义项为准，不以单个汉字或某一地读音为准。

`FlavorVariant` 是同一个风味在某个方言点下的读音变体，保存 IPA、拼音/罗马字、文白读、变调信息和官方认证状态。县镇之间读音差异优先进入变体，不把“同一个概念的不同读法”拆成多个风味。

`Package` 是文字包装，表示正字、借字、俗写、拟音写法等检索入口。`FlavorPackage` 记录风味和包装之间的主写法、同义写法、假借或争议关系。

`Dialect` 是方言点树，支持父子层级。查询父级时包含所有子方言，查询子级时只查该子级。

`Shelf` 是主题货架，用来组织风味或罐头。

单字和字音不作为独立一等实体。单字写法进入 `Package`；声韵调、文白读、地区等资料只有在服务具体义项或录音时进入 `FlavorVariant` 或 `Nameplate`。

## 关系原则

- 罐头与铭牌是一对多：同一段录音允许多个用户提出不同写法、释义和证据。
- 铭牌同时指向风味与包装：它记录“这段录音属于哪个义项，以及我主张用哪个写法表达”。
- 风味与包装是多对多：一个风味可以有多个写法，一个包装也可以连接多个义项。
- 风味与变体是一对多：读音、地区、文白读、变调属于变体层。
- 主铭牌是当前共识，不是永久真理：投票、认证或后续考据可以改变主铭牌。

例如“行”这种多义字，`Package(text="行")` 可以连接“行走”“行业”“可以/好”等多个 `Flavor`；“行走”这个 `Flavor` 也可以连接“行”“走”“趁行”等多个 `Package`。用户搜索“行”时先进入包装，再看到其下不同风味；进入“行走”时再按方言点展示各地读音变体和罐头。

## 治理边界

v1 只实现可追溯的主张与权重，不实现 AI 聚类或自动正字裁判。后续可以在 `Flavor` 或扩展提案模型上加入相似风味提示、合并提案、地区主理人认证等能力，但这些都不能替代铭牌层的证据记录。

## API 边界

新 API 统一挂载在 `/api/` 下，由 DRF router 暴露资源。旧词典式 `/words`、`/pronunciation`、`/characters` 入口不存在。

读接口默认开放，写接口需要旧系统 `token` header。后端通过 `guantou.authentication.HeaderTokenAuthentication` 复用现有 JWT 解析逻辑。

## 状态机

`Can.status`：

- `unlabeled`：无铭牌。
- `pending`：已有铭牌，等待社区或管理员校验。
- `tentative`：社区暂定。
- `verified`：正品认证。
- `disputed`：存在争议。
- `rejected`：已驳回。

`FlavorVariant.status`：

- `draft`：草稿。
- `verified`：已认证。
- `rejected`：已驳回。
- `disputed`：争议。

`visibility` 仍表示是否对普通用户可见，和状态流转分离。
