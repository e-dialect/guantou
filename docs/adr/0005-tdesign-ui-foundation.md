# ADR-0005：采用 TDesign 作为通用界面控件基础设施

## 状态

Accepted

## 背景

前端同时使用 uni-app 原生控件、ColorUI、uni-ui、自定义基础组件和 TDesign。不同页面重复维护输入高度、间距、按钮、加载与反馈样式；H5 原生 input 在叠加 padding 和 `border-box` 后还会把内部文本区域压缩到 0px。项目需要在不重做品牌业务视觉的前提下统一通用控件，并允许逐页迁移。

## 决策

- TDesign UniApp 是按钮、表单、反馈、加载、空态、选择器和列表单元等通用控件的标准库。
- 高频、稳定语义通过项目原语封装；复杂低频组件允许页面直接使用 TDesign。
- 项目设计 Token 继续保存品牌和明暗主题，统一映射到 TDesign CSS 变量。
- 迁移按页面推进；基础设施先提供原生表单兼容高度，待遗留控件归零后删除。
- 不用 CI 扫描旧控件，通过 `frontend/AGENTS.md`、迁移台账和代码评审约束。

## 后果

### 正面

- 表单尺寸、校验、加载和反馈行为有单一实现。
- 页面迁移可以独立评审，不需要一次性重写全站。
- TDesign 升级或跨端兼容调整集中在原语和主题桥接层。

### 负面

- 渐进迁移期间会暂时并存新旧控件和兼容样式。
- 项目原语需要维护一组刻意收窄的稳定 API。
- 复杂组件直接使用 TDesign 时，页面仍需理解其原生接口。

### 中性

- 品牌卡片、沉浸首页和页面壳继续由项目维护，不机械改写成 TDesign 布局。

## 备选方案

- 页面全部直接使用 TDesign：实现快，但 `v-model`、主题、反馈 context 和跨端差异会重新散落。
- 所有 TDesign 组件都包一层：隔离完整，但会复制大量低频 API，维护成本过高。
- 一次性全站迁移：最终状态统一，但改动和回归面不适合当前页面数量与测试覆盖。
